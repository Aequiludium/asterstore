# 性能测量

已有普通绑定、重复定位和元数据预览的 I/O 行为测试；新增本地生命周期基线脚本。它测量库的控制操作与普通字节文件读取，不测量 Polars/Arrow 查询吞吐。

```bash
uv run --locked python benchmarks/lifecycle.py --output /tmp/asterstore-baseline.json
uv run --locked python benchmarks/lifecycle.py --publications 50 --files 100 --no-durable
```

默认使用临时目录、10 次发布、每次 20 个 128 字节文件、7 次重复取中位数；开启持久同步。--parent 可以指定测量所在文件系统，--storage-label 用于记录介质/挂载配置。目录在测量后清理，输出 JSON 可保留。

[本地 v2 样例结果](results/local-v2.json) 记录 Python、平台、数据规模、durable、缓存说明，以及发布、打开 current、重复路径选择、引用创建/释放和元数据预览耗时。重复路径选择包含断言开销；直接读取与通过绑定读取使用同一批文件。参考名字重复使用，每次按 released revision 重建，预览中只有一个已释放名字。

结果是单次本地小规模、热缓存且操作系统缓存未受控的观察；实际存储介质未识别，也未隔离所有系统负载。读取对照按固定先后顺序执行，不足以推出两者的稳定性能差异。没有数据引擎、并发写入或物理 GC，不应推导生产吞吐、零开销或共享挂载资格。

对象复用的新增文件/字节数测量见下文；实际回收的小规模无争用样例见下文；锁等待和大规模运维内存仍需单独测量。新增引擎测量使用同一数据、查询和缓存条件，结果见下文 Parquet 读取与清单规模。

## 单分区更新的写入量

```bash
uv run --locked python benchmarks/incremental_write.py --files 20 --bytes-per-file 1024 --output benchmarks/results/reuse-local.json
```

全量重写与复用模式使用相同初始数据，只改变第一个分区。脚本分别统计新增数据文件、数据字节、保持原路径的共享文件和预览可回收对象；数据目录统计在计时后进行，不属于库的读取或预览路径。两种模式均 durable=True。

[本地样例](results/reuse-local.json) 中，20 个 1 KiB 分区更新一个分区，全量方式新增 20 个文件、20 KiB；复用方式新增 1 个文件、1 KiB，19 个文件保留原路径。该计数不包含控制元数据，不代表设备实际写入量。两个模式各测一次，缓存未清理、设备未隔离；时间只用于复现，不能据此宣称吞吐或延迟提升倍数。复用不重新同步共享字节；样例的源发布同样使用 durable=True。


## 共享对象的实际回收

```bash
uv run --locked python benchmarks/collection_lifecycle.py > /tmp/collection-local.json
```

[本地样例](results/collection-local.json) 有 20 个 128 B 文件，连续 5 次更新各复用 19 个文件。一次 collect 退役 5 个旧发布，只删除 5 个不再使用的文件；当前 20 个文件完整保留。记录预览、包含同步的 collect 和完成操作重试的耗时，均为无锁争用、热缓存下的单次样例，不代表冷缓存、生产吞吐或断电保证。控制记录全仓扫描及同步成本会随历史和日志增长；元数据压缩尚未实现。


[本地样例](results/candidate-residuals-local.json) 包含 4 个未提交候选（2 个未封存、2 个已封存）、16 个 256 B 文件。分别测量显式目录/字节诊断、持久放弃以及固定计划清理；清理后保留控制记录和空目录。单次无争用、热缓存的小规模样例只用于复现治理成本，不代表规模化性能、冷缓存或故障持久性资格。

## Parquet 读取与清单规模

```bash
uv run --locked --extra polars python benchmarks/parquet_read.py --output /tmp/parquet-read.json
```

`--files 1 16 128` 默认测量三档文件数，每个文件 4096 行、两个整数列、Zstd 压缩，durable=True。每档只创建一个 current 发布，随后分别测量：

- 原生 Parquet 写入与包含 seal/fsync 的 commit。
- 显式 open 的耗时和 Python tracemalloc 内存峰值；内存单独测量，不污染查询计时。
- 缓存全部路径、单文件 key 和四分之一清单选择。计时含 Python 循环/调用开销，每个样本平均 1000 次调用。
- 全部、单个、四分之一文件上同一个过滤/聚合查询的直接与适配读取，两者使用同一批文件，构造计划到 collect 都在计时内。直接路径提前选好；适配路径在计时内选择，反映接入额外成本。查询结果在计时后校验。

两条路径各自预热，7 轮交替先后顺序；原始样本和中位数都保留。直接/适配查询固定 `glob=False, hive_partitioning=False`，避免比较不同的引擎行为。记录引擎版本、线程池大小、平台、缓存与存储标签；`--parent` 可切换挂载位置。`--storage-label` 由测量者填写，不自动认定设备型号。

[本地样例](results/parquet-local.json)：Python 3.12.12、Polars 1.44.2、引擎线程池 144，文件数 1 / 16 / 128，总行数 4096 / 65536 / 524288，实际 Parquet 字节数 15509 / 248144 / 1985152。存储设备未知，数据刚写入、OS 缓存不受控，未隔离主机负载。

| 文件数 | open 中位数 ms | Python open 峰值 bytes | 缓存全量选择 μs | 直接完整查询 ms | 适配完整查询 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 0.160 | 5992 | 0.283 | 4.785 | 4.737 |
| 16 | 0.393 | 11230 | 0.282 | 6.130 | 6.414 |
| 128 | 2.092 | 94116 | 0.280 | 66.479 | 64.018 |

该样例说明应将随清单增长的 open 成本和缓存后的路径选择分开观察。查询时间接近，差值含引擎调度与环境噪声，不代表适配器使查询加速或零开销。最大压缩数据不到 2 MB，不能推导大型 Parquet 数据吞吐；也没有冷缓存、原生引擎 RSS、锁等待、并发 GC、历史/引用/日志积累或 NFS 测量。全仓治理的规模成本是下一项独立测量。


## v4 候选成员构建

```bash
uv run --locked python benchmarks/managed_membership.py --output /tmp/managed-membership.json
```

该脚本独立测量 path 声明和不可变成员清单构造；不写数据字节，不执行完整 seal/commit。记录源码 SHA-256、Python/平台、文件数、FileSet 全量校验次数，避免用耗时阈值代替复杂度证据。为分离元数据成本，冻结阶段使用候选内部 builder 的 snapshot 测量点；它不是新的公开 API。每档只测一次，durable=False，本地临时目录、缓存和负载未受控，无 RSS 测量。

[本地样例](results/managed-membership-v4.json) 中，1,024 / 4,096 / 25,000 / 100,000 成员的构建约为 0.094 / 0.376 / 1.706 / 6.036 秒，冻结约为 0.011 / 0.046 / 0.192 / 0.772 秒。逐项声明的完整 FileSet 校验为 0 次，冻结阶段为 1 次并处理 N 个对象。旧审计脚本在 1,024 成员上记录 524,800 次累计对象复核；修复后不再逐项重复完整清单校验。

这些数据只支持成员构建成本的判断，不能推导真实文件发布、批量 reuse、全仓治理、冷缓存或共享挂载的吞吐。reuse 仍需持久化完整保护快照，不属于这个线性构建结论。

## v4 历史、数据集、引用和回收日志

```bash
uv run --locked python benchmarks/governance_scale.py --output /tmp/governance-scale.json
# CI smoke；语义与计数断言，不设置不受控环境下的耗时门槛
uv run --locked python benchmarks/governance_scale.py --history 1 3 --datasets 2 --references 0 2 --logs 0 2 --repeats 1
```

[脚本](governance_scale.py) 在独立临时目录中通过真实公开 API 建仓、发布、保留与回收，不伪造控制文件。默认按四个独立维度测量，不构造全笛卡尔组合：

- 单数据集累计 1 / 100 / 1,000 次发布，每次新增一个 128 B 对象；发布数包含 current。
- 1 / 32 / 100 个数据集，每个只有一次发布。
- 0 / 32 / 128 个保留名字；固定三次发布，名字交替使用 OBJECTS/METADATA，全部指向第一个发布。因此引用数不等于不同被保护发布数。
- 0 / 10 / 100 个已完成 GC 日志；只有一个 current，历史计划为空。这只隔离日志数量成本，不代表大量非空删除计划。

每个场景报告建仓耗时、控制文件/字节及数据文件/字节数；current open、缓存选择、GC 前后 preview 的预热后三次原始样本与中位数；另跑 Python tracemalloc 测量操作自身的峰值，**不是进程 RSS**。retain/release、实际 collect、已完成计划重试各执行一次，记录带探针的总耗时。

探针只在基准脚本内安装并在退出时恢复：计数 `Path.read_bytes` 成功/尝试次数、返回字节、不同控制路径、`Path.iterdir`、`os.fsync` 和 `flock` 获取；记录 inventory、控制证据同步、精确删除的耗时。它不是完整 syscall 跟踪，不把返回字节当成物理磁盘流量。fsync 时间包含在同步/删除阶段中，阶段数字不能相加。锁获取时间只说明无争用开销，未测争用等待。读取计时和内存测量不安装探针，变更操作计时包含探针开销。

脚本断言所有场景的 current open 仍只读 marker/current、没有目录枚举；已绑定选择没有被探针记录的治理操作。引用保护、准确删除数、当前字节保留、完成重试不再调用删除也有断言。计数检测补充既有 I/O 契约测试，不替代它们对其他文件 API 的禁止检查。

[本地样例](results/governance-scale-v4.json) 为 Python 3.12、单进程、durable=True；数据刚写入，OS 缓存和主机负载未受控，存储介质未知。源码与脚本 SHA-256 随结果保存。`--no-durable` 仅改变受管发布设置，治理操作仍然强同步；可使用 `--parent` 和 `--storage-label` 明确测试文件系统。

| 发布 1,000 | 670.57 | 7,002 | 10.878 | 5.348 | 4.163 |

**观察与工程含义：**

- 所有场景 current open 都只读取两份控制记录，观测中位数约 0.19–0.36 ms；治理历史没有进入普通读取的全仓扫描路径。这不说明大型单发布清单的 open 成本不增长。
- 1,000 次发布删除 999 个旧对象后，preview 为约 1.034 秒、8,005 次控制读取、17.104 MB Python 峰值；控制文件由 7,003 个增为 8,005 个。**删数据不会缩短控制历史**，退役/计划/进度增加了后续扫描证据。
- 同场景 collect 执行 11,049 次 fsync，其中 fsync 总耗时约 2.106 秒；完成重试执行 8,017 次 fsync、零删除。重试仍重新验证和同步全仓控制证据，不能当作常数成本的状态查询。
- 当前设计适合显式安排治理批次，调用者不应在每次读取或轮询中执行 collect。频繁生成新的空 GC 计划也会积累扫描成本。尚不能据此给出普适的运行频率或容量上限。

本轮没有变化成员比例、共享对象拓扑、海量文件同发布、非空日志长期累积、并发锁等待、冷缓存、原生引擎 RSS、多客户端或故障恢复规模曲线。后续优化应先保留权属、退役和重试语义，再比较索引/压缩方案；本样例不证明线性上界、生产吞吐或共享挂载资格。
