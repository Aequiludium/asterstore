# 架构与边界

## 数据模型

仓库包含相互独立的数据集。每个数据集的 head 保存 revision、current 和可空的 rollback。版本由一份不可变清单描述，清单把逻辑成员名映射到该数据集内的文件。

一个成员可以是 Parquet、JSON、二进制文件或其他普通文件。业务元数据和数据文件使用相同的成员机制，因此可以在一次发布中一起生效。核心不理解 schema、日期、质量规则或更新频率。

发布成功时，新版本成为 current，之前的 current 成为 rollback。回退将 rollback 提升为 current，并清空 rollback。安全性来自发布前的业务检查；仓库自身只验证结构和文件条件。

## 并发与寿命

每个数据集有一把协作式修改锁，覆盖 Draft 上下文、回退和清理。不同数据集可独立操作。expected_revision 用于拒绝基于过期状态的写入。

读取固定一次 head 和清单，不取得修改锁。文件不可变，因此发布不会干扰已经绑定的读取。Binding 不登记读者，也不保留文件；清理窗口必须由调用方协调，覆盖最后一次延迟 I/O。

Draft 是单次进程内对象。退出上下文释放锁，不自动提交。失败后可以基于当前状态重新准备；提交响应不确定时先检查 head。

## 空间与成本

每次发布写一份完整清单，成本与成员数量成正比。继承 current 只复用文件引用，变化的成员才需要新文件。

清理只扫描目标数据集，成本与其物理文件数和保留成员数有关。清理完成后最多保留两份版本清单，以及它们引用的文件。两次清理之间的过期文件、清单和失败 staging 仍会占用空间。

## 部署条件

核心使用 POSIX 文件锁、同文件系统硬链接和原子替换，默认同步文件与目录。调用方必须通过协作式写入保持仓库完整，不能原地改写封存文件。

持久化同步、原子可见性和备份是不同能力。双版本提供操作回退；硬件损坏、外部篡改和完整数据备份由部署环境处理。

核心范围是数据集级别的两个版本，不提供跨数据集事务、任意历史查询、读者租约或跨进程 Draft 恢复。
