# 实施路线与验收

状态：2026-09-26。目标依据 [治理规范草案 0.1](spec/README.md)。当前运行时是 `0.1.0.dev0` 和受管开发协议 v3，以及新声明登记协议 v4，不能把新规范中的概念当成已经实现的 API。

## 已交付基线

- uv/uv_build 项目、职责子包、类型信息、零第三方核心运行依赖、独立发行包检查。
- 明确成员的内存/磁盘绑定；普通选择不做治理 I/O；显式刷新。
- 受管发布、generation 冲突、封存候选与恢复；本地多进程失败测试。
- 同仓同数据集对象复用、具名固定保留、预览、退役、固定计划物理回收与恢复。
- 候选显式放弃、残留诊断和私有文件清理。
- 可选 Polars 接入、真实 Parquet 生命周期、1/16/128 文件的本地热缓存读取测量。
- 上一实现阶段 Python 3.11/3.12 均有 212 项通过测试；这是现有协议证据，不是新规范验收结果。

当前不足：发布依赖图尚未接入 v4；无确定性布局协议；无业务附件固定关联、Release/公开 Pointer 及发布依赖保留；控制记录长期积累；未通过 NFS 写入资格。

通用模型、能力约束和恢复语义优先于旧 Aster 兼容。以下阶段用独立文件数据集验收；Aster 接入和生产迁移另行安排，不阻塞核心交付。

## 下一阶段的交付顺序

### P0：模型与协议评审

先把新语义落实为可执行的模型和 wire format 草案，再修改状态机。

**首项已落地**：v3 独立逻辑身份规则、4096 UTF-8 字节持久上限、原 ID 的安全 token 定位、v1/v2 读取兼容与写入拒绝；十类控制记录的打包 Schema、正反 golden fixtures 和生命周期测试。细节见 [v3 协议](protocol-v3.md)。 Python 3.11/3.12 各 254 项测试通过，ruff/mypy、全部示例、wheel 和 sdist 重建隔离安装通过。只读核对真实 AsterStore 当前 delivery 的 32 个来源发布 ID，均可原样编解码；这不证明既有目录治理接管已完成。这不表示 P0 全部完成：新模型持久接入、附件及统一数值边界仍待实现。

**第二项已落地**：新输入 Declaration、显式 FileSet、Member/Object/Locator、managed/registered 合法能力组合、资源根捕获，已接入 Binding 与 Polars。该阶段完成声明和读取，持久登记随后在第三项接入；受管提交和元数据/对象保留随后在第四、五项接入。详见[声明模型](declarations.md)。Python 3.11/3.12 各 309 项测试通过，ruff/mypy、全部示例、wheel 与 sdist 重建隔离安装通过。

- 拆分逻辑 ID、成员键和 locator；来源 publication_id 原样保留，控制路径由安全 token 生成。
- 定义 registered/managed 能力组合、声明/对象保留、资源映射、布局和附件。
- 明确 Publication、Release、Pointer 与固定 Retention 的权威来源；不给尚未实现的模型添加假 API。
- 制作下一格式的 JSON Schema、正反 golden fixtures 和状态转换表；确定新版本/必需功能门槛，旧 v2 不被静默改义。
- 评审确定标识符长度/数值边界、资源绑定和模板编码、记录原子生效点、幂等保留窗口。这些 wire 细节尚未冻结。

验收：A-02、A-25、A-26 的格式部分；模型约束和能力非法组合有测试。可以在本地隔离目录开始新格式实现，不能升级真实仓库。

**第三项已落地**：v4 Store/Publication/Object 权威记录、64 位有符号整数边界、必要功能门槛、Store 范围对象身份约束，以及 registered 持久登记、重新打开、原子 current、固定操作重试与恢复。此项完成了第一条持久链路，managed 与直接保留/GC 的统一随后继续推进。见 [v4 协议](protocol-v4.md)。Python 3.11/3.12 各 368 项测试通过，ruff/mypy、全部示例、wheel 与 sdist 重建隔离安装通过。

**第四项已落地**：v4 managed 候选、创建者记录、成员别名、同数据集对象复用、封存恢复及两种发布共用的原子提交逻辑；必要功能门槛隔离旧实现。当时保留、GC 和候选清理尚未接入 v4；直接保留与 GC 随后由第五项完成。见 [managed v4](managed-v4.md)。验证包括原有全量回归、两种发布共享提交边界，以及 managed 进程竞争和强制终止恢复；本地验证不等于 NFS 或断电资格。

**第五项已落地**：v4 直接 metadata/objects 保留、候选复用保护、退役、固定计划回收与恢复、显式候选放弃；不包含发布依赖图、元数据压缩和残留物理清理。见 [治理 v4](governance-v4.md)。Python 3.11/3.12 各 458 项测试通过，静态检查、全部示例和 wheel/sdist 重建隔离安装通过。

**第六项已落地**：v4 已放弃候选的私有与安装残留清理、严格创建权属与复用隔离、固定清单预览/执行/恢复、几何进度检查点和进程终止恢复。保留控制身份和空目录，不自动扩大删除范围。见 [清理 v4](cleanup-v4.md)。Python 3.11/3.12 各 510 项测试通过（本阶段新增 52 项），ruff/mypy、全部示例、wheel 与 sdist 重建及隔离安装验证通过。普通 current open 仍只加载 format/current，清理不增加读路径成本。

**独立审计已闭环**：四项实现问题与一个规范缺口已修复，新增 25 项回归测试，Python 3.11/3.12 各 535 项通过。普通读取成本边界保持不变，见[审计修复记录](audit-fixes-v4.md)。

**规模证据与首版范围已整理**：候选成员构建覆盖至 100,000 个成员；v4 治理分别测量至 1,000 次发布、100 个数据集、128 个引用、100 个空计划日志，公开控制读取、Python 峰值、同步与删除成本。所有场景 current open 仍只读两份控制记录；控制历史不会因数据回收而缩短，完成重试仍有全仓同步成本。见[测量报告](../benchmarks/README.md#v4-历史数据集引用和回收日志)及[首版范围与冻结检查](release-scope.md)。这不是完整 P4 或格式冻结验收。

下一步是依据这些证据完成公开 API/协议冻结评审，明确旧接口稳定性与开发格式兼容边界，Apache-2.0、维护入口和变更记录已补齐；冻结后确定最终版本和发行制品。以下完整规划仍有未实现内容，不能把有限本地版本等同于全部规范交付。

### P1：已有目录接入与规则布局

- 持久登记和独立 control_root；registered 默认无数据删除权、无对象保留承诺。
- 实现 explicit 与 deterministic 的闭合成员定位，保持 eager Binding 选择无文件 I/O。
- 逻辑成员映射与固定应用附件关联；引擎仍使用原生文件路径。
- 实现一个无金融依赖的既有目录示例。
- 用独立外部生产者示例验证 registered 无删除权、无外部字节保留承诺；Aster 的 JSON/pickle 提取不进入核心实现。

验收：A-01 至 A-11、A-23/A-24 的登记部分。独立示例的来源声明、单文件、分区文件和样本查询对应；禁止读路径隐式迁移、自动复制和数据目录写入。

### P2：发布与公开元数据关联

- 将新成员和能力模型接入已有候选、提交和恢复机制，保持只写改变对象。
- 提供可选 Release 与 revision 条件公开 Pointer，区分 current、公开选择和任务固定输入。
- 定义桥接外部 exports/delivery 的先保护、后公开、最后释放顺序；fixed 业务附件随声明提交。

验收：A-12 至 A-16、A-24。跨多表只承诺选择组合原子性，异常后不出现公开但无所需保留的目标。

### P3：依赖保留与治理接管

- 实现 provenance / retain_metadata / retain_objects 和两层可达性。
- 扩展现有 GC 与恢复，registered 对象持续排除在删除范围外。
- 在独立模拟结果仓库中验证公开根、任务保留和跨数据集依赖；每个消费者拥有独立引用。
- 用外部生产者验证管理权边界：未转移写入/GC 协调权时，新引用不能保护外部系统控制的物理数据。具体旧系统迁移另行设计。

验收：A-17 至 A-22 及 A-19 的进程竞争；失去最后根的环可回收，metadata 保留不自动永久保留所有数据。

### P4：规模证据与元数据维护

从 P1 起记录基线，本阶段集中验证真实规模及历史积累，不把优化提前到功能语义之前。

- 按 [测量计划](spec/conformance.md#31-下一阶段测量计划) 分开测成员数、历史、引用/依赖、日志、锁等待和同步。
- 依据证据决定是否引入分层清单、反向索引、checkpoint 或数据库索引；任何缓存都不是未经验证的删除授权源。
- 实现压缩前先明确重试窗口、对象归属证明和退役身份保存策略。

验收：A-22、A-27；成本曲线与恢复证据公开。可先发布能力受限的版本，但不得宣称无限历史成本稳定。

### P5：部署资格与开源发布

- 依据实际部署需求，在指定共享挂载的隔离测试目录验证多客户端锁、可见性和故障恢复；A-28 独立验收。
- 完成公开 API/协议兼容矩阵、迁移说明、许可证决定、贡献/安全报告入口、版本变更记录和制品验证。
- 发布说明明确本地与共享挂载的不同支持范围，不以路径可读替代写入资格。

本地有限功能版本不必等待所有 NFS 场景，但必须如实限制支持范围。任何生产切换、写入/删除和服务故障注入都是后续明确的运维任务，不由本轮设计任务执行。

## 完成的判定

每阶段用“实现接口 + 持久记录 + 验收场景 + 环境证据”确认交付。一个独立 Parquet 示例说明引擎接入可行，不能代替 Aster 业务兼容、全仓治理或共享挂载验收。

## 独立的后续 Aster 接入

核心模型稳定后再选择适配或重构 Aster。可以重新组织元数据、目录与公开 API，不要求透明替换。是否保留旧生产流程、如何提取 pickle、是否导入历史与 pin，由应用迁移方案决定；这些要求不得反向添加核心特例。生产切换必须完整解释保护范围和协调权，但不因此把旧治理算法保留为新库标准。

## 明确暂缓

跨仓库原子事务和自动 GC、后台读者租约、完整表/查询引擎、业务 PIT、强制内容寻址/去重、自动孤儿删除，以及预先建立的通用插件系统。
