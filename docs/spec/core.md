# 核心语义

状态：目标规范草案 0.1。规范入口、术语与实现差距见 [README](README.md)。本文件定义语义，不冻结 Python 签名或下一磁盘版本的逐字段编码。

## 1. 职责和边界

**C-01** 核心必须管理存储身份、发布成员、位置声明、管理权、引用、保留关系与可恢复运维。不得解释交易日历、PIT、字段业务含义、因子依赖计算或质量合格标准。

核心不以兼容旧 Aster 为设计要求；旧目录、元数据格式与公开 API 只能作为用例，不能覆盖本规范的通用不变量。应用决定数据内容、逻辑分区和业务发布要求；引擎负责解码、过滤、投影和计算；库负责声明与文件的治理关系。库不默认重算内容 hash，不把完整验证作为普通读取的前置条件。

支持范围首先是 POSIX 路径可访问的文件数据；“类似 OSS”表示对象与生命周期管理方式，不表示已经支持 S3 API、远程对象服务或跨区域一致性。

## 2. 概念模型

| 概念 | 定义 | 不得混淆为 |
| --- | --- | --- |
| Store | 一个有稳定身份和统一协调规则的治理域 | 某个永久不变的绝对路径 |
| Dataset | 一组逻辑数据的稳定身份 | 物理目录、业务 schema 或因子类 |
| Publication | 某数据集的一次不可变存储声明 | 已冻结的外部文件内容或业务质量证明 |
| Member | 发布内唯一的逻辑文件成员，关联一个 Object | 候选目录中的相对文件名 |
| Object | 物理文件的声明身份及位置 | 必须读取内容才能得到的 hash |
| Layout | 从成员及固定规则解析位置的声明 | 动态目录 glob 或任意 Python 回调 |
| Binding | 已解析并固定的一份发布及定位结果 | 锁、租约、保留引用或最新数据视图 |
| Release | 可选的、固定选择一个或多个发布及业务附件的公开声明 | 跨数据集写入事务 |
| Pointer | 通过 revision 条件更新、可选择新目标的命名指针 | 永久不变的任务输入 |
| Retention | 有独立名字、固定目标及明确范围的持久保留需求 | 共享布尔 pin、身份认证或数据健康证明 |
| Relation | 来源记录或显式保留依赖 | 无条件保留全部历史的 lineage |
| Operation | 发布、登记、退役、清理等可解释和恢复的操作事实 | 普通读取的隐式副作用 |

首版 Member 一对一关联 Object；同一分区可包含多个不同 member_key。成员 key 唯一；同一物理对象可以被多个发布引用。若使用者给同一对象多个逻辑别名，必须显式声明，不自动按路径或内容去重。

### 2.1 身份与路径

**C-02** `store_id`、`dataset_id`、`publication_id`、`release_id`、`object_id` 是不透明的逻辑标识符，分别在声明的作用域内唯一。发布完整身份是 `(store_id, dataset_id, publication_id)`。实现必须接受来源 ID 中的冒号、点和斜杠，按精确字符串比较，不偷偷做大小写折叠、Unicode 归一化或来源 ID 重命名。

ID 必须非空、可编码为 UTF-8 且不含控制字符；协议必须在冻结时规定统一长度上限。当前 v3 已为 dataset_id、publication_id 和引用 name 规定 4096 UTF-8 字节持久上限；v4 也已将该上限应用于 Store、Object、Member、资源和操作等逻辑身份。ID 不直接用于拼接磁盘路径：路径 token 由实现编码或 hash 生成，读回时必须核对原 ID。标识符 hash 不等于数据内容校验。

**C-03** member_key 属于发布中的逻辑命名空间；locator 属于物理位置空间。受管相对 locator 必须防止绝对路径、空段、`.`、`..` 和控制目录越界。root 是显式资源绑定，不从业务 ID 推导。为某些操作系统限制文件名，不能反向限制所有逻辑 ID。

member_key 也按精确逻辑字符串比较，不自动继承 locator 的分隔符含义；首版语法及长度上限在 wire format 中统一规定。

同一受管 object_id 一旦提交，不允许绑定另一份字节或另一归属；没有强制内容寻址。可变外部对象的身份只指向其位置声明，不承诺跨时点内容相同。

### 2.2 根目录与管理权

**C-04** 控制元数据根目录和数据资源根目录可以分开。Store 的协调规则、锁和权威记录位于明确的 control_root；数据通过资源标识和相对 locator 定位。

已绑定对象捕获其资源映射；资源迁移后必须重新绑定。受管目录移动是显式、停写并验证后的部署操作，不能在运行中将同一 store_id 指向两份可独立写入的副本。副本分叉必须获得新身份；备份本身没有自动成为第二生产仓库的权限。

根目录软链接可作为部署入口，不要求普通读取逐次 resolve。受管删除需要在运维边界检查真实管理范围，不能跟随数据子树中未知的符号链接扩大删除范围。登记可以声明边界，不能凭一个路径字符串证明独占管理权。

## 3. 能力组合

**C-05** 以下能力必须分开表达。它们是保证声明，不是开启任意布尔组合的开关；实现只接受已定义、可兑现的组合。

| 维度 | 需要表达的事实 |
| --- | --- |
| 文件管理权 | 库管理的对象；仅登记的外部对象 |
| 字节可变性 | 受管协议保证不覆盖；外部生产者声明不变；外部可变或未知 |
| 历史发现 | 只承诺当前声明；支持指定历史声明查询 |
| 成员闭合性 | 固定明确成员；固定规则及闭合键域 |
| 保留范围 | 声明及必要控制信息；受管对象及其声明 |
| 协调能力 | 哪些生产者、引用变更和回收者实际参加同一协议 |
| 持久性 | 本次边界执行的同步，以及复用来源的已有保证 |
| 环境资格 | 已验证本地环境；指定共享挂载环境；未验证 |

### 3.1 首版两种接入

| 行为 | managed：库管理的发布 | registered：既有目录登记 |
| --- | --- | --- |
| 数据写入者 | 遵守库发布协议的生产者 | 外部生产者保持自己的流程 |
| 初次接入 | 新文件写入受管范围，或显式迁入 | 保存声明；不要求复制或扫描全量数据 |
| 文件可变性 | 提交后不得覆盖，更新使用新对象；允许复用旧对象 | 必须明确外部声明，默认可变/未知 |
| 发布原子性 | 原子切换完整声明；已就位的受管成员保持不变 | 只原子提交登记声明，不承诺外部多文件快照 |
| 普通读取 | 固定声明和路径，无自动保留 | 固定声明和路径；实际字节可能已经变化 |
| 声明保留 | 支持 | 支持 |
| 对象保留 | 支持，但仅约束遵守协议的操作 | 首版拒绝，不能用 metadata 保留冒充 |
| 数据删除 | 权属与可达性同时满足后可以执行 | 禁止；仅可按策略清理库自己的登记元数据 |

registered 的“生产者声明不可变”是证据来源，不自动赋予库删除权、锁协调或对象保留承诺。可变外部数据使用旧声明读取时，结果描述必须暴露该较弱能力，不能命名为内容快照。

**C-06** 原地覆盖、current_only 和保留期限是不同概念。当前只保留最新数据的策略可以建立在不覆盖的受管对象上，也可以用于外部可变位置。当前 `PhysicalHistory` 的迁移必须显式展开这些事实；不得把旧 current_only 记录解释成受管不可变数据。

普通按历史 ID 打开的可用性由已声明的历史策略和退役状态决定；受管对象被明确保留时，应允许通过该保留引用重新绑定。支持历史查询不意味着历史永不回收。

### 3.2 管理权转移

**C-07** registered → managed 必须是显式接管操作：说明精确对象范围、原写入者停止或参与新协调的证据、可变性处理、保留需求迁移与失败恢复。修改 capability 标签不能授予删除权，也不能把既有文件变成不可变对象。

首版登记验收不依赖原地接管。复制进入受管范围可以作为独立方案，成本和取得保证的时点必须公开；不得默认复制整个既有仓库。

## 4. 成员与布局

**C-08** 发布成员必须在声明层面闭合，不根据读取时目录中新出现的文件改变。首版支持两类描述：

1. **explicit**：固定 member_key → object_id/locator 映射；适合不规则文件、增量替换和跨候选复用。
2. **deterministic**：固定规则版本、基路径、模板及有限键域；适合稳定命名分区。键域可以是明确列表，或内置通用类型的闭合范围与排除项。

规则不得执行任意代码或查询外部服务，不允许动态 glob。日期按自然日的闭区间可以纯计算；交易日、不规则缺口和业务排除集由生产者提供并固定为列表或不可变键域附件。不得用当前安装的交易日历重新推导旧发布成员，更不得据此决定删除。

模板编码必须可逆或能证明在键域内无碰撞，不能由值注入分隔符逃逸根目录；重复逻辑键、路径冲突和不支持的规则版本在声明边界拒绝。缺失的“已声明成员”在引擎读取时正常报错，不自动缩小范围。稀疏布局必须显式表达键域，不把 coverage 起止日期当作完整性证明。

**C-09** 增量更新必须显式形成“新逻辑成员 + 未改变成员复用”的完整发布。替换某逻辑键时产生新对象映射；仅因两个文件 basename 相同，不得自动覆盖或移除旧对象。库不要求为复用成员重新读取、hash 或同步文件内容。

逻辑成员与物理对象分离，不意味着所有数据都必须分区，也不意味着核心认识业务分区含义。

## 5. 绑定与读取成本

**C-10** 普通路径为：解析必要控制记录 → 绑定声明及资源位置 → 选择成员 → 原生引擎读取。

| 阶段 | 允许的治理成本 | 禁止的默认行为 |
| --- | --- | --- |
| 构造入口/导入 | 内存操作 | 建目录、加载引擎、连接环境 |
| open/bind 持久声明 | 必要控制记录读取、格式/身份/能力/关系结构检查 | 扫描数据目录、逐数据文件预检、全仓历史扫描 |
| Binding 成员选择 | 内存索引或确定性路径计算 | 重读 current、stat/exists、心跳、续租、写 pin |
| 引擎执行 | 引擎必需的 footer、文件访问和数据扫描 | 将引擎 I/O 宣称为治理预检；偷偷换绑或吞错 |
| 显式 refresh | 构造新 Binding | 原地改变其他持有者的旧 Binding |
| 显式 inspect | 请求范围内的数据/元数据访问 | 因检查未运行就拒绝所有普通读取 |

首版采用 eager Binding：成员选择所需控制信息必须在 open 时准备完成，保证绑定后定位无文件 I/O。未来分层清单若引入懒加载，必须提供不同且可观察的接口/成本约定，不能无声改变 Binding.files 的契约。未显式加载的业务附件不属于 files 所需信息。

**C-11** 保留引用不证明数据健康；成功 bind 不证明物理文件存在。显式检查按 metadata / existence / format / checksum / application 分层，报告检查范围、时间和实际完成层级；外部可变数据的检查结果不得当作永久证明。

普通读取必须保留真实错误，不自动返回空数据、重绑定 current 或执行恢复。空发布是合法声明；需要 typed empty table 时由拥有 schema 的应用/引擎适配器决定。

## 6. 提交、公开与多数据集选择

### 6.1 数据集提交

**C-12** 单数据集发布是首版数据提交单位。受管流程必须保证：

```text
创建候选并进入写入协调
  → 写入和关闭新增文件
  → 固定成员、附件和保留依赖，封存恢复信息
  → 必要同步、安装新对象
  → 在协调内检查预期 generation 及依赖目标状态
  → 原子提交完整发布选择
  → 完成所承诺的控制/目录同步并返回
```

权威记录之间的安装次序和唯一生效点由下一版磁盘协议定义；本文不把多个文件各自 rename 等同于一个事务。冲突不得自动覆盖。响应丢失必须能以原操作身份查询结果；重试不把较旧发布重新设为 current。

复用对象继承原有持久性。新操作的 durable=True 不能自动升级旧对象字节的保证。持有仓库写入/GC 协调期间才可准备对象；退出未封存候选不等于提交、放弃或授权清理。

registered 提交只固定导入的声明和证据来源。若外部生产者正修改数据，核心不能把这次登记包装成多文件原子快照。

### 6.2 公开选择

**C-13** 默认的 dataset current、对外公开指针与固定消费者输入是三个角色。Pointer 必须通过 expected_revision 条件更新；Retention 目标固定，释放自己的引用不得解除其他名字的保护。

可选 Release 固定选定的 publication 身份、每项所需保留范围以及业务附件身份。Release 可以只含一个数据集，也可以表示一个 delivery 批次；不是所有用户都必须使用 Release。

一个受管公开指针选中 Release 时，其要求的保留关系必须与指针生效处于同一协调提交。新目标先取得保护，旧目标只在新指针持久生效后退出保护；中断允许多保留，不允许出现公开但无保护的窗口。

**C-14** 一个 Release 的原子可见性只保证读者取得完整的发布选择组合，不保证各数据集同一时刻生产，更不冻结 registered 的可变字节。首版 Release 自动保护只跨同一 Store 协调域；跨 Store 原子提交和保留不支持。

同域 Release 可以包含受管数据与仅登记数据，但必须逐目标报告保留范围，不能把部分对象可保护的批次称为全量数据快照。

若使用方继续维护独立的外部 JSON/pickle 公开指针，适配器先建立新版本独立名字的 Retention，再原子持久更新外部指针，最后释放旧公开指针所属的 Retention。崩溃残留按操作记录诊断；不可在尚有旧读者但无任务保留的情况下承诺它们继续可读。该桥接不提供跨两个系统的通用事务。

## 7. 保留关系

**C-15** 关系有明确类型：

| 类型 | 意义 | 参与保留 |
| --- | --- | --- |
| provenance | 来源解释，可指向外部身份 | 否；目标消失可保留身份或 tombstone |
| retain_metadata | 为解释源发布保留目标声明及必要控制信息 | 是，仅元数据 |
| retain_objects | 需要目标受管对象及声明持续可读 | 是，对象加元数据；目标能力不足则拒绝 |

应用可以把某类 lineage 转为 retain_objects，但核心不得把全部 lineage 默认升级为保留，也不得偷偷将无法兑现的对象保留降级成 metadata 保留。

首版依赖目标采用同仓完整 publication 身份，整发布保护；局部分区依赖保护和跨仓自动协调另行设计。数据对象跨发布复用与发布依赖是不同关系：复用必须保护对象，但不必永久保留来源发布处于可打开状态。

### 7.1 两层闭包

**C-16** 运维分别计算：M = 必须保存的声明/控制信息；O = 必须保护对象可用性的发布。

- 声明级 Retention 目标加入 M；对象级目标加入 M 和 O。
- current 和公开 Pointer 按所属能力及目标声明播种：managed 的可读 current 进入 O；registered current 至少进入 M，不获得外部字节保护。
- 对 M 中发布，显式 retain_metadata / retain_objects 目标声明进入 M；provenance 不扩展闭包。
- 只有源发布在 O 中时，其 retain_objects 边才将目标加入 O。只留审计声明不会把所有上游数据永久留住。
- 对 O 的成员对象取并集，再叠加活跃/可恢复候选保护。重复对象只计一次，图遍历需处理重复边和环，并重复传播直到 M/O 均不再增长；环本身不是根，不能自我永久保留。

保护 metadata 不禁止数据退役，退役后仍可 describe 声明，但 open 数据必须返回明确已退役状态。引用/依赖不得复活已退役的 managed 对象发布；需要重新可读则创建新发布。元数据 compact 不得删去 M 中记录或未完成操作所需证据。

**C-17** 建立对象级 Retention、提交对象依赖及公开切换必须在同一 GC 协调域内校验目标尚可用，不能“先查存在，稍后写引用”。检查控制状态，不逐文件验证字节。新保留引用不能修复先前丢失的文件。

## 8. 回收、恢复与压缩

**C-18** 数据删除的必要条件为：库具有管理权、目标不在对象可达集、无活跃/可恢复写入保护、控制信息足够解释归属、计划与退役事实已持久化。仅“不在 current”“mtime 很旧”或“扫描不到引用”都不够。

preview 只解释当前观察；execute 在协调下重新计算。恢复只能在原计划的确切范围内继续，发现新保护就收缩范围。未知类型、损坏的治理相关记录、未知必须功能或不完整闭包必须阻塞受影响删除；首版无法证明错误局部化时可以阻塞全仓，必须公开这种成本与可用性边界。

registered 外部文件永不进入默认数据删除集合。没有索引的未知文件进入诊断，不通过全目录递归删除处理。诊断、放弃候选、清理私有残留、退役发布和压缩控制记录分别报告。

**C-19** 索引是优化，权威状态另有记录。压缩必须保留未完成操作、仍被引用的声明、退役身份和必要的幂等水位；写入新检查点并确认可恢复后才能移除被替代记录。原来源已退役但对象仍复用时，必须保留独立的归属证明，不能依赖永不删除的原候选日志。

未定义下一版检查点格式前不提供压缩命令。首版不可承诺无限时间内可重试所有已清除操作；超过明确重试窗口的请求必须返回过期，不能当作全新操作再次执行。

## 9. 扩展边界

引擎适配器消费 Binding 和路径，不进入发布/GC 权威解释链。业务适配器解释 schema、PIT、角色和时间，并生成核心声明。管理权、协调域、retention 和成员闭合性只能由已定义的核心功能扩展改变；任意附件或第三方回调不得暗中决定删除范围。

新能力先增加可测试的语义和格式要求，再增加便利 API。不会以本规范为由立即建立通用插件系统、元数据数据库或远程服务。
