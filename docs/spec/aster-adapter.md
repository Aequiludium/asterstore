## 2. 元数据映射是应用选择

旧 delivery 使用 JSON、因子治理使用 pickle，只说明两套现有实现，不构成新库必须复刻的结构。核心治理事实统一由版本化 JSON 表达；业务附件按内容中立地关联，不执行应用解码器。

应用可选择：

- 重构生产端，直接生成新核心声明及应用元数据。
- 显式导入所需旧状态，由 Aster 侧可信程序提取 JSON/pickle 中的事实。
- 仅登记既有文件，保留外部生产者，接受无数据删除权和无外部字节保留保证。

不要求保存每一份旧元数据，不要求双写，也不把“保存 pickle 附件”当成治理已经迁移。需要维持的业务语义由应用验收，不能靠核心猜测旧字段含义。

## 3. 可选映射方向

| 来源事实 | 通用模型中的可能表达 | 由应用决定的部分 |
| --- | --- | --- |
| 一张原始表或一个物理产物 | Dataset / Publication | 数据集边界可以重新设计，不强制复用 owner |
| 单文件或分区产物 | explicit / deterministic 布局 | 固定成员键域、路径映射、日历与缺口 |
| delivery/exports 的公开选择 | Release / Pointer，或应用公开记录 | 是否替换旧公开接口 |
| 消费任务需要固定输入 | 独立 Retention | 消费者身份、保护期限与保留范围 |
| 因子 lineage | provenance / metadata / objects 关系 | 哪些依赖确实需要保留，不自动照搬旧 GC |
| schema、PIT、业务角色 | 应用附件或应用版本记录 | 编码与业务解码完全留在应用侧 |

这些是目标模型映射，尚未实现的类型以核心规范与路线图为准。来源身份可以原样保存；如应用选择新的数据集边界或新身份，应保留必要的来源映射，不以无声重命名掩盖变化。

## 4. 两类接入及其真实保证

**仅登记**适用于暂不调整旧生产者的情况。外部文件仍由旧系统更新和回收，新库无删除权。metadata 保留只保护登记声明，不能阻止旧 GC 或生产者覆盖文件；因此没有通用的“新引用自动变成旧 pin”承诺。

**接管治理**适用于生产者准备遵守新协议的情况。新 managed 对象遵守新库的不可覆盖、提交协调、保留与回收规则；旧程序必须停止绕过协议更新或删除这些对象。可以使用新目录与新 API，不要求稳定旧路径。跨表生产依然不因一次 Release 切换而成为数据事务。

应用可以重算新产物而不导入全部历史。若选择迁移已有产物，必须识别仍需保护的输入、公开目标和在途状态，明确保留、完成或放弃，并保留源数据备份和必要身份映射。这是实际切换的正确性要求，不是要求新库永久保留旧状态机。

## 5. 独立接入项目的验收

在通用能力实现后，再为选定的应用方案定义验收：

1. 在隔离数据或只读来源上验证业务声明、成员定位及读取结果；允许应用接口变化。
2. 用隔离受管产物验证新公开选择、独立任务保留、依赖关系与中断恢复。
3. 若部署在共享挂载，单独验证目标环境的跨客户端写入与回收。
4. 若要生产切换，明确停写、协调权转移、所需保护、备份和失败处理方案。

不把旧 Aster 所有行为都作为期望结果。尤其不沿用共享布尔 pin、隐式来源保留或领域耦合 GC 作为新库标准；是否改进这些应用行为由接入项目决定。
