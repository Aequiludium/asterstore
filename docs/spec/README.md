# asterstore 治理规范

asterstore 是面向文件数据的独立治理库。既有目录登记与库管理的发布是同等重要的接入方式。它管理声明、成员、管理权、引用和运维操作，不拥有业务解释权，不要求数据采用专有表格式。

## 设计优先级

**通用治理语义优先于旧 Aster 兼容。** 继承的原则是边界检查、轻量读取、有限且明确的保证、显式保留与可恢复运维；不继承旧 API、目录结构、JSON/pickle 分工、owner 定义或 GC 实现作为核心约束。

当旧实现与核心不变量冲突时，调整 Aster 侧适配器/应用，或提供显式导入与迁移；不得为保持旧行为增加核心特例。Aster 适配与生产迁移是独立的后续项目，不是通用核心交付或发布的前置条件。当前实现不支持历史开发格式；未发布草稿只保留在 Git 历史。

## 核心决定

1. 逻辑身份、逻辑成员、物理位置分开；发布 ID 不按路径校验，不按内容 hash 定义。
2. 原目录可只登记元数据，不复制数据、不改变现有生产者、默认无删除权。
3. 管理权、字节可变性、历史发现能力、保留范围和持久性分别声明；分别说明保证边界。
4. 核心权威记录采用版本化、可独立解释的 JSON；业务附件可保留 JSON、pickle 或其他格式，核心不执行其解码器。
5. 普通绑定不产生保留。可变公开指针与固定任务保留分别表达，独立消费者拥有独立引用。
6. 来源记录与保留依赖分开。跨数据集依赖在同一协调域内显式声明，跨仓库自动保留不进入首版。
7. 闭合文件清单与确定性规则定位都支持；读取不扫描目录，不调用运行时业务日历推断已发布成员。
8. 不要求每次读文件做 exists/stat、schema 或 checksum 校验。内容 hash、内容寻址和去重均非默认要求。
9. 回收必须由管理权和完整保留关系证明，先持久计划与退役事实、再精确删除；未知对象不因未被引用而自动成为垃圾。
10. 开源交付包括语言独立的格式说明、能力矩阵、失败语义、兼容规则和可复现证据；不以功能数量代替这些约定。

## 本轮范围

首个实现仍是 Python + uv，核心零第三方运行依赖，Linux 本地文件系统先验收。引擎通过 optional extras 接入；Aster 的业务桥接由 Aster 一侧维护，核心不得反向依赖 Aster。无提前引入的后台服务、插件发现系统、分布式锁服务或完整查询层。
