# 元数据、事务与协议演进

状态：目标规范草案 0.1。本文规定记录职责与不变量；v3 已实现身份演进；v4 已实现声明、创建权属、直接保留与回收记录，精确字段见 [v4 协议](../protocol-v4.md)、[managed](../managed-v4.md) 和 [governance](../governance-v4.md)，其余目标模型仍待实现，不把下文示意字段当作已实现的 wire format。

## 1. 权威分层

**M-01** 同一个治理事实只能有一个权威来源；其他结构必须是明确的引用、证据副本或可重建索引。

| 层 | 权威事实 | 推荐表示 | 核心职责 |
| --- | --- | --- | --- |
| 库的治理记录 | Store 身份、管理权、发布成员、引用、保留边、退役与操作 | 版本化严格 JSON | 理解其语义并参与协调和 GC |
| 应用声明 | schema、PIT、字段角色、业务版本、公开映射 | 应用决定，通常 JSON | 保存不可变关联；不解释业务规则 |
| 附件及来源证据 | 原始 descriptor、publication、exports、legacy pickle 等 | 原格式不变或明确转换 | 保存字节/位置、格式和来源；默认不反序列化 |
| 缓存与索引 | 查询索引、对象反向索引、统计缓存 | 可选 JSON/SQLite/二进制 | 丢失后可重建，不得凭过期缓存授权删除 |
| 数据文件 | Parquet、Arrow、二进制及其他内容 | 原生格式 | 管理成员和位置，不提供通用解码 |

附件格式中立是通用能力，不是保留旧 Aster 两套元数据实现的要求；新应用可以完全不用 pickle，核心也不提供 Aster 专用字段或旧对象兼容层。JSON 与 pickle 同时存在不构成错误。错误是两个记录独立决定同一 current/保留事实，或某个业务字段未经核心声明就改变删除行为。

核心不依赖 pickle 解码。旧系统 pickle 中若包含需要参与治理的成员或依赖，必须由显式、受信任的迁移/适配程序提取为核心记录；把 pickle 作为不透明附件存下来，不等于已经完成治理适配。

### 1.1 业务附件

**M-02** 附件至少需要说明命名空间、格式/版本、来源身份，以及与哪个 Publication 或 Release 关联。与已提交发布关联的附件版本不可变；修改业务声明应形成新版本关联，不能覆盖旧发布绑定的声明。

附件有两类：

- **fixed**：不可变字节随控制提交进入库管理范围，或由已验证的不可变元数据记录引用。它属于该发布/Release 的必要控制材料，声明保留同时保留附件。外部固定附件若不能证明版本稳定，登记时可只复制这份元数据；不因此复制数据文件。
- **external evidence**：记录外部路径与观察时信息，允许来源后续改变。它不能作为保证绑定业务语义不变的唯一依据，不得冒充 fixed。

完整性 digest 可用于固定附件的提交、导入和显式审计；协议若让 digest 承担版本身份，就必须定义算法与确切输入字节。此要求不扩展为强制计算数据文件内容 hash，也不意味着每次 Binding.files 都校验附件。核心不以附件中的 pickle 对象、JSON 键名或动态插件执行路径决定保留。

不认识应用附件格式的客户端仍可绑定存储成员；需要解释该附件的应用必须自行明确报不支持，不能悄悄采用默认业务语义。

## 2. 记录族与更新方式

**M-03** 以下是语义记录族，可由具体协议合并存储，但不得合并其保证：

| 记录 | 稳定部分 | 可变部分及协调 |
| --- | --- | --- |
| Store/Resource | store_id、协调域身份、资源归属 | 配置迁移必须停写或用明确版本切换 |
| Publication | 逻辑身份、成员/布局、能力事实、附件、关系 | 退役事实独立表达；不原地修改发布内容 |
| Object ownership | 对象身份、创建者、受管位置 | 删除进度不改变原归属；不能仅从候选目录推断 |
| Release | 被选择发布、保留范围和应用附件 | 不原地换目标 |
| Pointer | 名字与指针类型 | target、revision，条件更新 |
| Retention | 名字、固定目标、范围、归属描述 | active/released、revision；重用名字必须条件创建 |
| Operation | 请求身份、预期版本、固定目标和计划 | 状态/进度；恢复不扩大原授权范围 |
| Retirement/checkpoint | 已退役身份、不可复活事实、幂等水位 | 显式压缩并保持可恢复性 |

“声明不可变”不要求永久保留每个重复副本；压缩后仍须能够给出等价权威结果。格式可以在 current 中嵌入完整声明以减少读取，也可以通过固定身份引用不可变记录，选择前必须测量，不因规范分层机械增加每次 open 的小文件数。

外部可变数据的同一 locator 可对应多份历史登记声明；这些声明不自动对应多份历史字节。库不得把路径相同推导为两发布内容相同。

## 3. 序列化和兼容

**M-04** 核心权威记录采用 UTF-8 JSON，必须拒绝重复键、非有限数字、错误类型和非法身份。版本、计数与 revision 使用明确范围的整数，不能把 bool 当整数。业务 timestamp 不作为并发提交顺序，generation/revision 由协调域决定。

每种记录的公开定义必须包括 kind、格式版本、字段含义、必选性、作用域、状态转换和示例。下一磁盘协议发布前交付 JSON Schema 与 golden fixtures；跨记录的一致性、锁和状态机由行为测试验证，不能由 Schema 代替。

**M-05** 仓库协议能力至少区分：读取所需、写入所需、回收所需。未知必须功能不能被旧客户端忽略：

| 未知内容 | 行为 |
| --- | --- |
| 目标读取所需的成员编码或布局规则 | 拒绝该绑定 |
| 写入协调或记录语义 | 拒绝相关 mutation |
| 会影响管理权、可达性或恢复的功能 | 拒绝相应 GC；无法证明局部性时全仓阻塞 |
| 明确声明可忽略的应用附件/注释 | 允许核心读取，保留原始关联，不给予治理效果 |

顶层未知字段默认拒绝；可扩展字段必须放入有命名空间和版本的扩展区。一个扩展若改变存储、保留或删除语义，就必须升级为受能力协商约束的核心功能，不能伪装成可忽略注释。

写入器的读改写不得丢弃它不理解但协议允许保留的信息。旧版本客户端拒绝不支持的仓库是可接受的，静默忽略保留关系则不是。

**M-06** Python 包版本、仓库磁盘版本、业务 schema 版本、来源 publication_id 分别演进。当前开发 v2 不应继续承载不兼容语义而无新的版本/功能门槛；逻辑身份演进现已分配为 v3；后续不兼容能力仍须新的格式/功能门槛。

正式兼容承诺应列出 supported read / write / GC 组合、升级和回退条件。0.x 阶段可进行显式破坏性变更，但必须说明受影响数据与处理方式（可为重建、显式导入或迁移，不强制为每个开发格式提供迁移工具）；普通 open 禁止自动迁移。旧 Aster 应用兼容与本库已发布协议的兼容政策分别管理。

## 4. 事务、失败与幂等

**M-07** 每个 mutation 必须定义：预期版本、精确目标、持久生效点、成功后的保证、响应不确定时的查询和恢复方式。后台线程、析构或普通读取不得隐式提交或释放保留。

| 场景 | 必须能解释的结果 |
| --- | --- |
| 数据写完、声明未提交 | 未公开候选；可诊断/恢复，不当作已发布 |
| 声明切换前发生冲突 | 旧公开状态不变；残留可解释 |
| 原子替换已发生、同步或响应失败 | 可能已经生效；按原 operation 身份查询，不假定失败未执行 |
| 公开新目标时进程退出 | 旧或新完整选择可见；所需保护不能先于旧指针消失 |
| 删除部分对象后进程退出 | 原计划可恢复；不会扩展到未知文件 |
| 旧 release/publish 请求晚到 | revision/generation 冲突；不撤销更新后的状态 |
| 同 operation_id 携带不同目标重试 | 明确身份冲突，不解释成新的操作 |

候选或操作 ID 可由客户端提前生成。幂等语义必须限定保留证据和有效窗口；过期请求不自动重做。失败报告至少包括操作身份、观察状态、失败阶段、已生效/可能生效的范围及恢复入口；具体异常类由 API 设计确定。

### 4.1 协调

**M-08** 所有可能改变可达性、对象归属或删除目标的操作必须参加同一个 Store 协调协议。首个本地实现允许仓库共享/独占锁及局部提交锁，但必须公布锁顺序和持锁范围。普通绑定及文件选择不持治理锁。

长候选持共享锁会推迟 GC，是明确取舍；运维不得在自己持有候选共享锁时申请冲突的全仓独占锁。候选、引用、公开选择与依赖的状态竞争必须有跨进程测试。

同一数据目录不能让两个各自不认识对方保护关系的回收者同时取得删除权。迁移期间新库仅登记旧目录，则其禁止删除规则可避免这种双重权威；待接管写入和回收时必须转移协调权。

### 4.2 持久性与部署能力

**M-09** 原子可见性、写入竞争控制和持久性必须分别声明。调用了 rename 不自动获得条件更新；调用了 fsync 不自动获得所有网络文件系统上的相同故障保证。

受管暂存与最终数据对象安装必须满足同文件系统原子操作的前提；外部跨文件系统输入应先复制到目标文件系统的暂存区域。control_root 与数据根分开时，必须明确各自的同步边界以及中断恢复次序，不能把这一配置解释成跨文件系统事务。

local-managed 的同步选项应保留明确的强/弱路径，弱持久性仍需满足可见性和冲突约定。复用来源、外部来源和新对象的保证分别报告，不能因一次强同步提交就重写历史能力。

正式支持 NFS 写入/回收需要目标挂载上的跨客户端锁、缓存可见性、服务端故障及重启恢复证据。可读 NFS 路径与通过 NFS 写入资格是不同支持级别；不能仅因检测到 nfs 类型就宣称已具备后端能力。

## 5. 库结构约束

封闭职责或预计独立演进的能力使用子包与明确接口，不把全部操作平铺在 repository.py。以下是演进方向，不是本轮已创建的源码目录：

```text
metadata/                # 核心值对象、记录、codec、格式兼容
registration/            # 既有目录登记、能力声明、接管规划
reading/
  layouts/               # explicit / deterministic 的纯定位实现
publishing/              # 单数据集提交与恢复
catalog/                 # Release 与公开 Pointer 的一致性
retention/
  references/            # 独立具名保留
  graph/                 # 元数据/对象保留闭包
  collection/            # 退役、精确删除和恢复
  cleanup/               # 已放弃候选的私有残留
inspection/              # 分层显式检查与诊断
storage/                 # 文件系统原语、协调、控制记录访问
integrations/            # 可选引擎，不承载 Aster 领域逻辑
```

小规模实现可把 graph 先封装在现有 collection 内；没有独立复杂性前不因目录图强制拆文件。跨子包通过 `__init__.py` 接口协作，内部导出不自动成为对外稳定 API。协议模型不能导入引擎或 Aster；Aster 适配包放在使用方。

## 6. 开源交付规范

**M-10** 声明“支持某能力”必须同时具备公开语义、实现、行为测试和文档，不把示意 API 写入可执行示例。正式发布前至少交付：

- 许可证及第三方依赖说明，由维护者明确选定；本规范不替维护者选择许可证。
- 安装、最小示例、能力矩阵、错误与恢复说明，核心安装不引入数据引擎。
- 格式说明、Schema、golden fixtures、升级/兼容说明和版本变更记录。
- 贡献指南、问题模板和安全问题报告入口；不宣称多租户隔离或不可信代码沙箱。
- uv 锁定开发环境、源码包/wheel 独立安装、最低 Python 与可选依赖边界验证。
- 性能脚本与环境说明、发布制品清单及可定位的源码版本；不把一次基线包装成 SLA。

## 7. 参考来源与采用范围

以下是本轮核对的外部依据；本规范的能力组合、M/O 闭包与接入分工是针对本项目提出的设计，不是这些项目的原文规定。

- [Apache Iceberg specification](https://iceberg.apache.org/spec/#snapshot-references)：参考固定快照、可变引用、保留策略与元数据原子提交的分层。我们不采用其表 schema、查询/行级删除模型，也不据此获得同等隔离级别。该规范同时区分元数据提交与具体存储实现，提醒我们不能用多次普通文件替换冒充原子事务。
- [object_store PutMode](https://docs.rs/object_store/latest/object_store/enum.PutMode.html)、[LocalFileSystem](https://docs.rs/object_store/latest/object_store/local/struct.LocalFileSystem.html)：参考覆盖、仅创建、条件更新等操作的区分，以及本地实现的同步配置；接口名称不能替代后端资格。
- [此前源码学习记录](../research.md)：Kartothek、Lance、delta-rs 等提供缓存、提交、孤立对象和恢复方面的参考。其已记录的固定版本结论保留，本轮未重新核验全部源码；不扩大此前证据范围。
