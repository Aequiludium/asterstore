| 指标 | 前 | 后 |

本轮所有场景的 inspect、metadata check 和完成态重试耗时均下降；首次 GC 在 1,000 次发布和组合场景反而更慢，不能宣称首次回收吞吐提升。组合场景 GC 的 inventory 探针耗时从 5.40 s 降至 3.15 s，但 fsync 累计耗时从 3.40 s 升至 6.95 s，同步次数均为 35,193。两轮存储/主机负载未隔离，因此记录这个差异，不据此推断固定加速或退化比例。

完整 inspect 的 Python 峰值分配增加约 2.67 MiB；metadata check 峰值略降。按次缓存有内存代价，未宣称所有查询都降低内存。

## 改动与边界

- 完整检查仍覆盖全部关系；每份控制记录每轮只读一次，相同内容复用不可变解码结果。缓存不跨调用，因此下次检查仍能发现新损坏。目录布局仍需遍历；没有宣称全仓检查为常数成本。
- 完成态重试改为核对原任务证据并同步完成记录，避免重新扫描/同步无关历史。它不再是全仓审计，不执行任何删除；新回收、未完成恢复仍进行完整关系检查和证据同步。原有最终目录 fsync 失败和 protected 结果保持测试通过。
- 新增 collection_status / cleanup_status。collection_status 固定三份记录、零目录枚举，但解析成本随所选计划大小增长。全库对象保护解释仍需要 inspect。
- 所有场景普通 current open 仍为两份控制记录，Binding.files 不发生文件 I/O；这些读取没有新增校验。
- 实际删除路径的 fsync 没有裁减。耗时波动中也含主机负载和存储同步差异，应结合确定性的读次数、同步次数及回归测试判断，不把单次加速比例作为性能保证。

复现参数与命令见[基准说明](../../benchmarks/README.md)。验证还包括 308 项测试、类型/格式/协议检查；Python 3.11/3.12 和隔离安装由同一 PR 的 CI 检查。
