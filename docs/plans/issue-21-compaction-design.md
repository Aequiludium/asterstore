# Issue #21 D：控制历史归档与压缩设计草案

日期：2026-10-13。状态：历史设计草案，D 已实现并复审。下文保留推导过程；最终格式和恢复规则以 [实现契约](../control-compaction.md) 为准。实现保留原路径身份入口，不减少小文件数，以逐条等价替换取代草案的全仓指针。A/B/C 的本地交付继续有效。本文不授权自动删除数据或控制历史。

## 1. 推荐结论

先做保留现有语义的归档与重复证据合并，不在首版引入按时间过期的请求。完整 current 保持独立；写入只查询本操作所需身份和对象证据；全面核验、归档构建、空间回收属于显式治理。

这里的“保留语义”指保留原有成功、冲突、退役、放弃与持久化恢复行为，不承诺已退役操作仍可成功提交。历史声明仍可 describe，原本允许的历史 open 继续受能力与退役规则约束。

这能降低重复控制字节、小文件数量和治理打开文件的成本，但总存储仍随历史唯一身份及声明增长。若要求空间有硬上限，就必须再改变历史查询和请求身份契约；仅增加 TTL 无法实现这一点。

以下依据当前工作区代码核对，不是拟议协议已实现的能力。

| 证据 | 当前消费者与约束 | 压缩必须保留的内容 |

当前 inventory 拒绝未知顶层目录，旧 marker 解码器只接受列出的 required_features 组合。不能把 checkpoint 放进去再假定旧 GC 会正确工作。归档后删掉原记录还会直接违反现有相等性与创建者校验，必须先修改权威读取协议。

## 3. 为什么不能直接设置重试天数

operation_id 是调用方提供的不透明字符串，没有可信时间或 epoch。若删除旧身份记录，收到相同字符串时无法判断它是首次请求还是过期重试。expected_generation 只能约束该数据集的一次提交，不能代替跨请求身份保留；换数据集或改变请求仍须冲突。

| 方案 | 能保留什么 | 代价与限制 |
| --- | --- | --- |
| 保留完整语义，归档正文并合并重复记录（推荐首版） | 现有结果查询、身份冲突、历史声明与恢复行为 | 历史身份和正文继续增长；需可寻址归档 |
| 永久身份凭证，正文超过窗口删除 | 可识别旧 ID 并返回 expired，不误执行 | 身份数量仍无界；describe 与恢复行为发生变化，需明确新契约 |
| 带可信 epoch 的新请求协议 | 可拒绝整个过期 epoch，减少逐 ID 永久凭证 | API/协议改变；旧任意字符串仍需遗留身份表或整体封存，不能自动推断 epoch |

首版不以 mtime、首次观察时间或 dataset generation 推断请求过期。未来若选择有限窗口，需要分别定义 publication、object、retention name、GC/cleanup operation 的身份存续，不能只处理 publication operation_id。

## 4. 权威 checkpoint 与归档边界

拟议结构是“权威 checkpoint + 切换后的活动记录 + 不可变归档正文”，另外允许可重建的加速索引。这里 checkpoint 是新协议明确规定的权威记录，不是 C-19 所称可丢弃索引。索引丢失可重建；权威 checkpoint 或归档正文损坏必须报错，不能当作记录不存在。

- current 保留完整原声明并由原子替换发布；默认 current open 不读取 checkpoint、归档或索引。marker 可以声明新功能，但不把历史解析引入 current 路径。
- 历史声明、固定请求和已完成任务正文以稳定身份寻址；同一完整声明可只存一份，其他权威记录显式引用。摘要用于完整性和寻址，不单独构成权属或删除授权。
- 对象创建证明独立保存 object_id、locator、byte_stability、creator 及可核验来源关系。生成时从原 request/seal/object 交叉验证，不从目录位置推断。
- 未完成发布、可恢复候选、未完成 GC/cleanup 原记录首版不迁移；其保护集仍参加治理闭包。终态对象被未完成任务引用时也不迁移该依赖闭包，先用保守边界降低恢复复杂度。
- 已释放 retention 也保留名称绑定和 revision；已退役发布继续保留原声明与退役证据；不存在“归档即解除对象保护”。
- archive 是本仓权威数据，首版不移到可选远端存储。不能把缺失归档当成 cache miss 后重新执行请求。

归档按独立可读取的块组织，避免一次历史查询必须解压全部历史。精确块格式、身份目录、校验覆盖与更新规则在协议实现前冻结；不在本草案虚构一个已验证的磁盘布局。

## 5. 切换、持久化与恢复

首版采用显式维护窗口，暂停写入与治理修改。仅取得 gc.lock 不足以保证候选没有在锁外构建；部署侧须停止所有写进程并释放候选句柄。锁粒度优化不与本阶段捆绑。普通 current 读取仍不参加治理锁。

1. **准备**：在协调锁内读取并全面验证现有权威闭包，固定输入集合和内容摘要。发现损坏或无法解释的所有权即拒绝迁移，原状态不动。
2. **构建**：写入独立临时输出，生成归档、身份目录及 checkpoint；逐项核对源记录覆盖、引用可解析性、保护集和终态结果等价。不得依靠加速索引证明完整。
3. **同步**：同步新文件及全部必要父目录；压缩不提供跳过此步骤的 durable=False 模式。未确认可恢复前不删除旧证据。
4. **启用协议**：首次迁移先持久化新 required feature，让旧程序明确拒绝。新程序必须支持“功能已启用、checkpoint 尚未激活”的过渡状态，仍以完整旧记录为权威。旧进程必须已经停用，marker 更新不能撤销旧进程缓存的能力。
5. **激活**：原子替换并同步单一 checkpoint 指针。它明确覆盖的旧记录由 checkpoint/归档替代，其余记录仍为活动权威。迁移期间没有并发写入，不能仅用时间判断覆盖。之后新写入按新协议检查活动记录和 checkpoint 身份表。
6. **清理**：用持久化固定清理计划删除已确认被替代的控制文件；逐项记录结果，支持重试。清理不删除对象字节，不更改 current，不扫描认领未知文件。

| 中断点 | 恢复依据 |
| --- | --- |
| 激活之前 | 旧权威记录仍完整；新临时输出不能授权删除。已启用新 feature 则由新程序恢复过渡状态 |
| 激活之后、清理之前 | checkpoint 与活动记录是权威；被覆盖旧文件只是待清理副本，不重复计入关系 |
| 清理中途 | 固定清理计划继续处理确切文件；缺失、损坏、内容变化分别判定，不能重做一轮无范围删除 |
| checkpoint/归档损坏 | 显式失败；不静默回退旧副本，因为可能已发生后续写入或部分清理 |

后续压缩遵循同样的激活顺序。历史查询可能持有旧归档定位，因此首版保留旧归档段；物理回收旧段另需停止历史读取的维护窗口或明确读者生命周期协议。不得为解决此事给默认 current 读取增加锁/引用计数。持久 writer.lock 文件不因候选已提交就删除，避免仍存句柄造成两个不同锁对象。

回滚不是把 marker 改回旧值。只有在停写且可以从新权威完整重建并验证旧布局时才能显式导出旧格式；否则保留新协议并向前恢复。

## 6. 性能目标与验收范围

沿用 [B 基线](../validation/issue-21-baseline-2026-10-13.md) 与 [C 报告](../validation/issue-21-c-2026-10-13.md) 的分项测量。C 已暴露的小批 reuse 反复重写 protection 成本，不会被历史压缩自动解决，应另列写入优化任务。

D 首轮测量记录：逻辑声明字节、重复证据字节、控制文件数、归档后总字节、首次治理读量/时间、任务重试读量、单次历史查询读放大、构建/清理时间、峰值内存、协调锁占用与恢复时间。分别扩大历史发布数和每发布对象数，保留无改善和变慢结果。

不承诺 O(1) GC。若仍需遍历全部历史关系，只减少文件数并不改变复杂度。将已退役历史从日常计算排除，需要 checkpoint 中的权威存活关系摘要及增量维护协议；它是后续独立优化，不能拿可重建缓存替代删除证据。

验收至少覆盖：

- 压缩前后相同请求、不同请求复用同 ID、retired/abandoned、弱→强重试结果相同；损坏证据不退化为未找到。
- 原创建发布退役但对象仍被 current/retention/候选复用；释放 retention 再取回同名；未完成 GC/cleanup 依赖闭包保留。
- describe 历史声明一致，历史 open 能力与退役判断一致；current open 控制读取数不增，Binding.files 不发生 I/O。
- 每次写入、同步、指针替换、删除前后故障注入；重复执行清理不扩大范围。
- 老版本面对新 marker 明确拒绝；新版本识别迁移过渡状态；禁止旧写进程混用的部署要求有可执行演练。
- 缺失/损坏归档、坏索引、未知文件、symlink、锁句柄存续、历史读取与旧段回收边界。

## 7. 后续实施拆分与讨论点

1. **D1：只读归档规划与成本归因。** 输出可合并重复记录、必须原样保留的依赖闭包、预计空间与文件数变化；不改格式、不删文件。这是下一步最小可验证实现。
2. **D2：冻结协议及恢复模型。** 明确 checkpoint/归档记录、身份查询、独立权属证明、过渡状态、功能标识与迁移兼容矩阵，再实现故障注入模型。精确格式未经这一阶段不得提供 compact 命令。
3. **D3：显式迁移与压缩。** 实现维护窗口、构建/激活/清理、历史查询和状态查询，以及分项复测。
4. **D4：另行选择有限窗口或增量治理。** 只有实测表明永久归档仍不能满足容量目标，才推进请求 epoch/过期语义；增量治理也需独立权威关系协议。

需要讨论的核心取舍：是否接受“保留现有历史与重试语义，但总存储随历史增长”。本草案推荐接受，先优化重复与文件布局；若业务明确需要硬容量上限，则应先定义哪些历史查询/重试可以过期，再设计新身份协议。两种目标不能通过一个默认 TTL 同时满足。
