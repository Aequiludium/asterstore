# Issue #21 workplan：读、写与运维治理分离

日期：2026-10-13。状态：A/B 已完成；按用户继续推进的指令，C 本地实现、回归与复测已完成，尚未发布。D 的分析、协议、压缩恢复、复测与独立复审已本地完成，尚未发布。

关联：https://github.com/Aequiludium/asterstore/issues/21

## 1. 已确认方向

读和写均允许调用方显式开启检查，默认不执行可选检查。运维治理提供独立、可调度的审计与维护。零额外读取开销指绑定后的选择与适配不追加治理 I/O；不意味着首次 open 无解析成本。发布成功表示提交成立及履行选定持久性，不默认代表数据质量验收。

本计划以已发布的 0.2.0 为行为基线。先界定契约并做分项测量，再改实现；不预定后续版本号。当前执行 C 的代码、文档、回归与复测，不提交或发布远端评论。

## 2. 职责与不可选约束

| 阶段 | 必须保留 | 默认不执行的可选工作 |
| --- | --- | --- |
| 读 | 支持的协议解析、必要声明结构与资源绑定约束、已有历史访问规则 | 数据存在性、格式、checksum、目录盘点 |
| 写 | 请求与对象身份、generation、路径与权属边界、复用保护、原子可见性、选定持久化顺序 | 数据健康检查、额外文件盘点、全仓历史审计 |
| 治理 | 删除时协调确认权属与保护关系、固定任务恢复证据 | 按显式命令选择范围、检查和维护策略 |

`check="none"` 不等于关闭协议解析或事务约束。`durable` 与检查选项正交，禁止通过关闭检查跳过承诺的 fsync。关闭检查后具体还需要哪些类型/路径探测，必须逐项从提交、安装和安全删除协议推导，不能笼统删除 `_verify_files()`。

## 3. 已采纳的检查接口方向

读写使用 `check`，默认 `"none"`。第一阶段使用单值，避免立即增加组合类型；format/checksum 是分支，不是假定存在包含关系的整数强度。

| 选项 | 范围与行为 |
| --- | --- |
| none | 无可选数据检查 |
| existence | 检查选定对象存在且为所要求的文件类型 |
| format | existence + 调用方提供的格式检查器 |
| checksum | existence + 调用方提供的可信 SHA-256 |

示意：`repo.open(dataset, check="existence")`、`writer.commit(check="format", validator=...)`。不增加长期全局隐式设置。参数拼写、报告/异常类型和签名在阶段 A 冻结。

- `format` 必须提供 validator；`checksum` 必须提供完整可信基准。缺失、格式错误或无关参数在启动检查前拒绝，不静默降级。
- 按唯一对象去重检查；摘要键使用稳定对象身份，避免别名重复检查。具体沿用现有治理 API 的 object_id 契约，核查跨资源与复用语义。
- 读检查绑定已选择的确切发布；不在检查中重新跟随 current。不新增锁、隐式 retain 或刷新。检查结果只是观察，GC 或外部修改可能使其随后失效。
- 首次提交及未提交恢复的检查必须在本次操作替换 current 前完成；检查失败时本次调用不推进 current。并发调用可能提交相同 registered 请求，因此不能仅凭本次检查失败推断操作未提交。用户回调不放进全局协调锁。调用方仍负责关闭写句柄并停止修改；协作式不可变假设不升级为防恶意篡改保证。
- 显式写检查覆盖最终声明全部唯一对象（包括复用对象），同步仍只针对当前操作承诺的数据；默认 none 不读取复用数据字节。第一阶段不增加仅新增对象 scope。
- 明确 `seal`、`commit` 与 `resume` 各自参数入口；避免 commit 的 none 仍通过 seal 隐式执行全面扫描。检查选项不改变固定提交身份，检查结果也不作为删除授权。
- 已提交重试无法保证“检查失败则此前未发布”：必须区分首次提交、未提交恢复、已提交结果查询/重试。已提交重试执行显式请求的检查；失败携带提交状态，不回滚。具体结果/异常结构在阶段 A 细化。
- extra-file inventory 单独设计：只适用于有明确所有权的候选/受管范围，不能递归盘点 registered 外部资源根。先不塞入 existence，也不提前承诺作为读写参数。

现有 `governance.check(level=...)` 保持现有默认 metadata、范围和报告契约，不能直接更名或改变默认。复用底层对象检查器，不让读写借用全仓 inventory。治理 checksum 缺失基准目前作为报告发现处理，读写采用严格参数验证；共享底层机制不强行统一两者的错误策略。检查组合可留到实际需求出现后增加。

### 3.1 入口与恢复语义

| 入口 | 行为 |
| --- | --- |
| open | 对本次绑定的确切声明执行选定检查；describe 保持纯元数据查询 |
| managed commit | 每次显式调用都处理本次 check 参数，不以已 sealed 作为已检查证据 |
| managed resume | 只恢复候选；随后 commit(check=...) 决定本次检查，不持久化回调或检查通过标记 |
| registered register / resume_registration | 同样接受 check；非 none 时显式提供 resources；默认不访问外部数据 |
| seal | 固定成员声明、执行必要安装约束与选定持久化；不缓存数据健康结论 |

已 sealed 的内存快路径和从磁盘恢复的 sealed 路径均不得绕过本次 commit 检查。安装前检查使用私有路径，安装后恢复使用已安装路径，复用对象使用原对象路径；检查目标按固定声明解析，不从最新 current 重选。

已提交重试的语义：none 维持已有幂等行为；非 none 检查原提交的对象，失败明确携带“操作已提交”的状态，不回滚、不重复发布。若检查期间无法确认提交状态，标记 unknown 并指引状态查询，禁止推断未提交。操作状态判断与并发退役等关系在协调边界复核；检查本身不承诺期间对象持续可用。具体异常载荷与状态枚举在 A 冻结。

### 3.2 默认 none 的具体边界

对 managed 新增声明文件保留最小安装要求：必须存在、为普通文件且路径不得逃逸或通过链接重定向；这属于安装所承诺对象的成立条件，不执行整个目录的额外文件盘点。durable=True 还需打开新文件进行同步，错误必须传播。durable=False 只省同步，不允许发布根本没有形成的新对象。复用和 registered 在 none 下不做数据存在性验证，身份与权属证据仍按事务协议核对。existence 因此能对最终声明的复用/外部对象提供额外检查，而不是承诺 none 完全没有任何数据路径访问。

本计划不允许 managed 声明缺失的新文件；这项最低安装要求与可选数据健康检查分别记录、分别验收。

### 3.3 未声明文件与清理的实施门槛

当前 installed cleanup 遇到超出 sealed 创建证据的文件会整体拒绝；关闭全面盘点将使这条路径更容易触发。不能仅增加一个诊断入口便声称恢复闭环完成。阶段 C 在默认关闭目录扫描前，必须一起定义并验证：安装前/安装后未提交/已提交三种状态的未知文件报告、可操作的恢复路径、以及清理已知对象与保留未知文件的结果语义。

采用保留未知文件、显式报告残留的治理原则。删除仍仅限当前治理接口有权处理且具备权属证据的对象；不得直接扩张现有 cleanup 的 complete 含义，也不得依目录位置生成删除权限。若安全恢复仍要求调用方处理未知文件，应提供准确文件清单与恢复后重试步骤，并明确其非自动修复。方案未闭环前不交付默认行为切换。A 阶段选择保持 installed cleanup 对未知项的拒绝行为，以只读盘点、明确人工移走未知条目、重新预览/清理形成首版恢复路径；不在 C 引入自动部分清理。

## 4. 已知实现切入点

- `publishing/_candidate.py`：`_verify_files` 混合递归盘点、文件类型检查与同步；seal 和 install 均调用，install 在提交锁内。
- `publishing/transactions/_commit.py`：逐对象身份与控制证据处理、同步和完整 current 写入；避免只优化 JSON 而忽略复用成本。
- `registration/_operations.py` 与 `repository.py`：registered 注册和恢复目前无资源映射参数；显式检查必须新增调用时资源映射，不将环境路径写进固定注册身份。
- `reading/_loading.py`：普通 current open 维持现有 marker + current 路径；历史读取单独记录原有 I/O，不误称全部读取都只读两文件。
- `governance/inspection/_checks.py`：抽取可针对确定对象集执行的检查能力，保留治理汇总报告。
- `governance/_inventory.py`：当前全仓关系重建；后续将操作必要状态与全面审计区分。

## 5. 实施阶段与交付

### A：冻结行为契约

交付逐项检查责任表、公开 API 草案、错误行为表、兼容性说明和当前测试到新契约的映射。落实第 3、8 节已采纳的范围与状态语义，细化异常载荷、残留报告、恢复步骤及同步顺序，不重新悬置已采纳的取舍。默认由严格候选盘点改为 none 是可观察行为变化，必须写升级说明；磁盘格式不变不代表 API 行为无变化。

### B：分项基线

扩展现有 benchmark，分别测首次大量新增、少量新增 + 大量复用、历史增长后的首次 GC、已完成任务重试。区分 durable true/false 与检查档位。

记录：成员/对象数、历史数、新增与复用比例、控制记录读取数量与字节、序列化时间与字节、目录扫描/stat 次数、fsync 次数与时间、锁等待/持有时间、总耗时和峰值内存。记录设备、文件系统、缓存条件、Python/依赖与源码 SHA，保存原始报告；插桩计数与无插桩耗时分开，不虚构冷缓存。

先小规模验证工具，再扩大代表性负载；不预设百分比性能目标，以基线确定预算。阶段 A/B 可以先落地，不提前承诺格式改造。

### C：读写可选检查与内部职责拆分

抽取共同对象检查器，接入确定范围的读写检查；拆分最小安装约束、可选盘点与持久化。保持原子 current、复用保护与恢复顺序。逐项消除同次操作重复读取或同步，只有证据充分才移出锁；不扩大缓存生命周期以牺牲状态正确性。

补齐独立候选检查方案，避免移出的目录盘点没有运维入口。对于未声明文件：不进入绑定、不自动纳入普通 GC；检查如何报告、何时允许清理以及证据来源先定义再实施。诊断与清理权限分开，不凭目录归属认领任意文件。

### D：治理长期成本（独立后续设计）

根据基准设计显式历史归档/压缩。保留完整 current，不给读方增加 manifest 追踪或增量合并。明确 current/保留历史、未完成操作、对象权属、退役身份、幂等结果与过期请求的权威证据。

先决定永久幂等或有限重试窗口，再设计 checkpoint 原子切换及恢复。不能直接删除已提交候选或对象记录。格式/required_features 是否需变化，须根据旧读写器和旧 GC 能否正确解释新布局判断。锁粒度调整另行论证，不与本阶段捆绑。

## 6. 验收与回归

- 默认 current open 不增加控制读取/数据 stat/scan/hash/锁；Binding.files 在任何模式下均无新增文件系统 I/O。
- 各检查选项覆盖缺失文件、类型错误、格式失败、摘要不匹配、缺失基准、别名去重、registered 资源映射与复用对象。
- 首次提交检查失败时本次调用不替换 current；并发相同 registered 请求的最终提交状态须另行确认。候选仍可按封存规则恢复/放弃；结果错误区分检查失败与已提交后响应失败。
- 同 generation 竞争、seal/安装/current 前后中断、弱持久到强持久恢复、已提交重试、历史访问语义均有对应测试。
- 并发 reuse/retain/GC 不误删；不使用过期检查结果授权删除。用户回调不持全局锁，异常不会泄漏锁或产生隐式发布。
- 不可选路径/权属约束覆盖链接与异常文件类型；none 下未声明文件的行为、诊断和清理边界有测试与文档。
- 现有 governance.check API 回归、格式兼容性、示例和发布检查通过；性能报告保留退步与无改善结果。

## 8. 已采纳决策与评审处理记录

评审：[GPT-6.1 Sol 独立评审](issue-21-workplan-review.md)。评审中的计划行号指初稿，源码行号对应 0.2.0 基线。以下修订已按用户指令吸收为计划决策；不表示运行时问题已修复。具体实现细节与验证交付仍按 A/B/C 推进。

### 状态与失败语义

| 操作状态 | 本次显式检查 | 失败/恢复规则 |
| --- | --- | --- |
| 未封存 | 固定声明后，检查私有新增路径与复用路径 | 不发布；不得假定 seal 失败后仍可修改成员；需修补字节时用新操作重做 |
| 已封存未安装 | 仍执行本次检查，不能因 sealed 快路径跳过 | 保留封存声明；可重试瞬时检查失败或放弃，禁止改写 sealed 字节 |
| 已安装未提交 | 检查已安装新增路径与复用路径 | 不推进 current；保留恢复证据；可重试或显式放弃/清理 |
| 已提交 current/historical | 检查原声明，显式报告已提交状态 | 不回滚 current；失败不得伪装未提交；none 保持原恢复行为 |
| retired/abandoned | 保留既有不可恢复提交限制，不用强检查复活 | 走显式状态查询/治理，不重建已退役对象 |

默认重试的持久化行为保持原契约。非 none 重试若检查失败，不承诺本次强持久升级已完成；错误需分别表达提交状态与本次持久化完成情况。并发注册可能在检查期间提交相同请求，最终状态需协调确认；不能靠检查前一次 status 推断。必要证据损坏或状态无法确认时明确 unknown。

### none 与 durable 最低要求矩阵

| 对象/条目 | none + durable=False | none + durable=True |
| --- | --- | --- |
| managed 新文件及受管根/父链 | 验证安装成立的路径与普通文件约束；缺失、链接重定向、目录/FIFO 等拒绝 | 相同约束，加新字节与必要目录/控制证据同步；同步失败传播 |
| managed 复用对象 | 核对身份/保护证据，不做数据健康探测 | 不同步复用字节；同步所依赖控制证据 |
| registered 外部对象 | 不访问外部数据 | 仍不访问或同步外部数据；只履行控制记录持久性 |
| 未声明条目 | 不递归盘点；未知文件不得自动取得 GC 删除权 | 同左；不承诺未声明内容持久化 |

对被检查的新对象，路径父链约束与文件类型约束不可只由普通 open/fsync 间接实现，以免跟随链接或阻塞在特殊文件。源/目标 rename 目录与嵌套目录项的同步顺序需在阶段 A 的实现映射中逐项保留。

### 入口与基准补充

- `bind` 第一阶段保持纯内存构造，不新增检查；检查入口为 open、managed commit、registered register/resume_registration 和显式治理。Binding.files/引擎适配器无延迟检查。
- open 检查覆盖绑定声明全部唯一对象，不是后续 files(keys=...) 的子集。写入同样检查最终声明全部唯一对象。
- checksum 使用 object_id 基准；managed 可先 seal 获取完整对象映射，再 commit(check="checksum", checksums=...)。验证对象集合与基准集合相等（空集合允许空映射），在数据检查前拒绝缺项/多余项；旧治理汇总语义不变。
- 基准增加 sealed/installed 恢复、已提交 weak→strong 恢复、纯复用/空发布、一次大批 reuse 与多次小批 reuse。检查拆分不承诺解决 protection 全量重写成本。
- 升级文档覆盖 publishing、API、compatibility 和相关规范；逐项映射旧 missing/extra/symlink/directory 测试。验证旧工具面对新允许状态的表现，不以字段未变化直接宣称混用完全兼容。
